## 1. Objective
Используя функцию проверки наличия товара на сайте магазина, просканировать внутреннюю сеть 192.168.0.X (порт 8080) на наличие админ-панели для удаления 'carlos'

## 2. Reconnaissance
1. Зашел на сайт, перешел на страницу первого попавшегося товара, там обнаружил кнопку 'Check stock'
2. С помощью Burp Suite Interceptor перехватил этот запрос
3. В запросе увидел что stockAPI принимает полный URL, а значит сайт уязвим к SSRF

## 3. Exploitation

1. Отправил запрос в Intruder
2. Поменял 'stockAPI' на 'http://192.168.0.X:8080/admin' 
3. Поставил payload markers вокруг 'X' в URL
4. В Payloads добавил числа от 0 до 255 (simple list)
5. Запустил sniper attack
6. В результате перебора IP-адресов обнаружил аномальной длины ответ с пейлоадом 122
7. В Interceptor поменял 'stockAPI' на 'http://192.168.0.122:8080/admin' и отправил запрос
8. Система проверки наличия мне вернула мне HTML админ-панели
9. В админ-панели кликнул на кнопку удаления 'carlos' и через Interceptor перехватил этот запрос, дабы получить endpoint этого действия на back-end'е (admin/delete?username=carlos)
10. Вернулся на начальную страницу товара, перехватил запрос проверки наличия товара, где заменил stockAPI на endpoint удаления 'carlos' (http://192.168.0.122:8080/admin/delete?username=carlos)

**Payloads:**
```text
Атака 1 (сканирование): Sniper + числа от 0 до 255 в последнем октете IP
Атака 2 (удаление): Прямой запрос к http://192.168.0.122:8080/admin/delete?username=carlos
```

**Почему это сработало:**  
На сайте существует SSRF уязвимость в функционале проверки наличия товара, которая обращается напрямую по URL без валидации. Это позволило:
1. Просканировать внутреннюю сеть 192.168.0.0/24, подставляя разные IP-адреса в параметр stockApi
2. Обнаружить живой хост с админ-панелью на порту 8080 по аномальной длине ответа
3. Обратиться напрямую к API-endpoint'у удаления пользователя, минуя необходимость интерактивного использования веб-интерфейса (так как SSRF возвращает сырой HTML, а не отрисованную страницу)

## 4. Result
Получен доступ ко внутренней сети и админ-панели, лабораторная работа решена

## 5. Key Takeaway & Remediation

**Что я узнал:**  
SSRF можно использовать не только для доступа к localhost, но и для сканирования внутренних сетей. Злоумышленник может перебирать IP-адреса во внутренних подсетях и находить скрытые сервисы (админки, базы данных, внутренние API), которые недоступны из внешней сети.

**Как защитить:**
1. Валидировать и whitelist'ить URL в параметре stockApi: запретить не только localhost, но и внутренние IP-диапазоны
2. Реализовать защиту на уровне сетевого firewall: блокировать исходящие запросы от приложения к внутренним сетям
